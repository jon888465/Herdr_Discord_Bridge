# ADR-0002：營運卡片存放於 plugin 狀態目錄並記錄流程

日期：2026-11-02。狀態：**已採納（Accepted，2026-11-02 使用者同意四項決定；同日補充決定 10、11）**。**部分取代 [ADR-0001](0001-portable-md-cards.md)**，範圍見文末「與 ADR-0001 的關係」。

> **本文只是決策，沒有任何程式或行為改變。** 營運卡片的位置、流程紀錄、`projects` 欄位與 bridge 的寫入都**尚未實作**；`CardStore` 目前沒有呼叫端，bridge 不讀寫任何卡片。

## 背景

ADR-0001 假設卡片是專案 repo 裡的 md 檔、用 git 保存歷史、執行態不進卡片。2026-11-02 與使用者討論後釐清：

- `docs/cards/` 與 `docs/card-examples/` 放的是**範例與設計文件**，不是營運資料。
- 實際開發用的卡片是 **herdr-discord-bridge 這個 plugin 自己的帳本**：記錄一張單從開單到結束的流程，像 log DB，**不進 git**。
- 各專案原本的 issue、README、CHANGELOG 等 md 照舊由 Agent 在專案裡寫，不由 bridge 代寫。
- 卡片要記錄這張單**改了哪個（些）專案**。

把卡片放在公開 repo 的 `main`（本專案 `origin` 為 PUBLIC）會遇到：`main` 有 ruleset，每次狀態變動都要開 PR；bridge 在被版本指紋監看的工作樹內寫檔，會改變指紋（`team ask --coding` 的指紋含未忽略的 untracked 內容）；Mantis 單可能含內部或客戶資訊，commit 進公開 repo 即公開；卡片進度與程式碼混在同一條 git 歷史，可能與分支衝突；多機器要自己同步 git。

## 決策

### 1. 營運卡片放在 plugin 狀態目錄，不進 git

- 位置：`<stateDirectory>/cards/`。`stateDirectory` 即 `src/config.ts` 的 `stateDirectory()`：環境變數 `HERDR_PLUGIN_STATE_DIR`，預設 `~/.config/herdr-discord-bridge/state`（目錄 0700，Team 任務的 journal 也在這裡）。
- 沿用 ADR-0001 的格式與工具：一卡一個 `.md`、受限 frontmatter 子集、`parseCard`／`serializeCard`／`importCard`、`CardStore(rootDir)`（`rootDir` 指向上述目錄）、`herdr-card-check`。
- `docs/cards/` 與 `docs/card-examples/` 維持範例與設計文件的角色，bridge 不讀寫它們。

### 2. 卡片是流程帳本（取代 ADR-0001 決定 2「執行態不進卡片」）

卡片記錄從開單到結束的流程：進度、結果、異動專案。卡片分兩個區域，寫入者不同：

| 區域 | 寫入者 |
|---|---|
| frontmatter 的需求欄位、`## 描述`、`## 驗收條件`、`## 待確認` 等 | 人（含 Agent 協助轉換） |
| `status`、`updated`、`projects`、`## 異動專案`、`## 流程紀錄` | bridge |

bridge 只**追加**到自己的區域，不改人寫的內容。

### 3. Journal 是執行狀態的權威來源，卡片紀錄由事件衍生且可重複寫入

Team 任務的 journal（`src/team-task-store.ts`）已是執行狀態的權威來源。卡片的流程紀錄由 journal 事件衍生，每筆帶事件 id，重複寫入同一事件不產生重複的紀錄行。卡片遺失或損壞不影響 journal 與任務執行。

### 4. 異動專案

- frontmatter 以 `projects: [專案名, ...]`（純量陣列，現有格式即可表達）取代單一的 `project` 欄位，方便搜尋與列表。
- **專案名稱 = `<機器 id>:<repo 目錄名>`**（使用者 2026-11-02 選擇），本機用 `local:`，例如 `local:Herdr_Discord_Bridge`、`agy-pod:Herdr_Discord_Bridge`。完整 repo 路徑與 remote 網址放在 `## 異動專案`，需要唯一識別時查那裡。
- 詳細資料由 bridge 追加在內文 `## 異動專案`，每個專案一段：機器、repo 路徑、分支、worktree 路徑、base 與 head commit、PR 連結（完整網址）。
- 現有 `project` 欄位暫時仍被接受以相容既有範例，之後移除。

### 5. 流程紀錄（提議的形式，細節於實作時定）

`## 流程紀錄` 只追加，每行一個事件：

```text
- 2026-11-02T08:15:00Z | started | 在 agy-pod 建立 worktree，分支 card/REQ-20261102-example | ev:3f2a9c
```

欄位為時間、事件名、單行說明、事件 id。說明不得含換行。

### 6. 專案文件不由 bridge 代寫

issue、README、CHANGELOG 等由 Agent 在該卡片的 worktree 裡依專案自己的規則修改，隨 PR 一起進專案。bridge 只彙整**結果**到卡片，不替專案寫文件。

### 7. 刪除與保留

卡片是狀態目錄裡的檔案，使用者可以手動刪除。已結束的卡被刪不影響系統；對應任務**執行中**時卡片被刪：暫停並詢問使用者（沿用 ADR-0001 決定 7），journal 仍在。

### 8. 多機器

卡片只存在跑 bridge 的那台機器；遠端 Herdr 機器不放卡片、不需要同步。`## 異動專案` 記錄每個專案所在的機器。

### 9. 隱私

狀態目錄 0700，卡片不進 git，因此 Mantis 等內容不會進入公開 repo。內容只在使用者主動匯出（Mantis、Notion）時離開。bridge 不把 Agent 的自由文字寫進卡片，例外的短文字也要通過機敏檢查（決定 11）。

### 10. 流程紀錄的大小：先提高上限，超過再輪替到旁檔

使用者決定（2026-11-02）：不為了 256 KiB 的整檔上限而限制紀錄，**先提高上限，真的超過再把舊紀錄放到旁檔**。

- **兩種上限分開：** 匯入來源不可信，上限 **512 KiB**（使用者 2026-11-02 由原本的 256 KiB 調高）；bridge 自己管理的營運卡片使用較高的上限，整檔硬上限 **1 MiB**、輪替門檻 **768 KiB**（兩個數字使用者 2026-11-02 確認）（硬上限的 75%，保留空間給單次追加）。`parseCard` 等已改成可帶上限參數（見「實作狀態」）。
- **輪替：** 追加一筆紀錄後若整檔會超過輪替門檻，bridge 把較舊的紀錄移到旁檔，**卡片只保留最近 5 筆紀錄**（使用者決定，2026-11-02），其餘全部移走，並留下一行指向旁檔的說明。旁檔沿用同樣的紀錄行格式，只增不改。輪替後卡片的大小大致回到沒有紀錄時的大小，因此輪替不會頻繁發生。
- **旁檔命名與位置：** `<stateDirectory>/cards/logs/<卡片 id>/0001.md`、`0002.md`…。**不可與卡片同層、也不可叫 `REQ-….md`**：目前 `CardStore` 的 `CARD_FILE`（`/^(REQ|TKT)-.*\.md$/`）會把任何這類檔名當成卡片，旁檔會被列為損壞的卡片。放在 `logs/` 子目錄下，`list()` 與 `existingIds()` 就不會看到它們。
- **崩潰安全：** 先建立旁檔（以不覆蓋的方式），再用雜湊比對更新卡片。兩步之間崩潰會讓同一批紀錄同時存在於旁檔與卡片；因為每筆紀錄有事件 id（決定 3），讀取時以事件 id 去重，重複不造成錯誤。重試時若最新的旁檔內容恰好等於這次要寫的，直接沿用，不再建新檔。
- **去重也要看旁檔（實作時發現，原文未寫）：** 輪替後舊事件的紀錄行不在卡片裡，若 bridge 重送同一個事件，只檢查卡片會讓冪等失效。因此卡片有指向旁檔的說明時，追加前也讀旁檔的事件 id 去重；沒有說明時不讀旁檔，平常不增加成本。
- **單次追加最多 200 筆，旁檔用絕對上限 1 MiB 讀取（實作時發現，原文未寫）：** 旁檔內容最多是「輪替門檻（硬上限的 75%）加上一批」，一批最多 200 筆（約 70 KiB），所以一定小於 1 MiB。若改用這張卡的上限讀旁檔，旁檔可能比卡片上限大而讀不回來，之後所有追加都會失敗。
- **單筆紀錄要有長度上限：** 「保留 5 筆」只有在每筆都是有界的單行時才保證卡片縮小。長度上限見決定 11。若人寫的內容本身就超過輪替門檻，輪替無法使卡片縮小，視為無法輪替，走下一項的保護。
- **超過硬上限的保護：** 輪替要保證卡片永遠不超過硬上限；若無法輪替（例如旁檔寫入失敗），bridge 拒絕追加並回報錯誤，而不是寫出無法解析的卡片。
- **實作影響：** 原本寫死 256 KiB 的三處（`src/card.ts`、`src/card-store.ts`、`src/card-check-cli.ts`）已改為依用途帶入上限，見「實作狀態」。

### 11. 流程紀錄的內容規則：結構化優先，自由文字受限且遇疑似機敏即整筆省略

使用者決定（2026-11-02）：採用「C 混合」，子決定 1 到 5 照 Agent 的建議。

**背景（2026-11-02 的實測）：** bridge 已有兩份重複且不一致的遮蔽邏輯（`src/handoff-evidence.ts` 的 `publicText`、`src/main.ts` 的 `redactHandoffSecrets`），也沒有針對遮蔽規則的專門測試。用 15 個明顯假造的機敏樣本實測，**只遮蔽 7 個、漏掉 8 個**：`github_pat_…`（細粒度 token）、AWS access key、JWT、單獨的 `Bearer …`、`API_KEY=`、`secret_key:`、含帳密的網址、資料庫連線字串。黑名單式遮蔽無法保證完整。因此**最強的保護是根本不把 Agent 的自由文字寫進卡片**。

規則：

1. **預設：結構化事實，不寫自由文字。** 紀錄由 bridge 以固定模板組出，只含它自己產生的有型別欄位：事件名、狀態、commit SHA、PR 網址、分支名、機器名、判定結果、次數與耗時、失敗的分類碼。Agent 的最終回覆、報告與工具的錯誤訊息**不寫進卡片**，細節留在 journal 與 Discord。
2. **例外：短自由文字**（例如失敗原因）可以寫入，但必須通過機敏檢查。**命中任一高風險樣式時，整筆說明改成固定訊息**（例如「內容已省略：疑似含機敏資料」），**不做局部遮蔽、也不拒絕追加**：事件本身（時間、事件名、事件 id）仍照常記錄，只是說明被省略。
3. **網址一律先移除帳密**（`user:pass@`）以及查詢字串中名稱像 token 的參數（名稱含 token、key、secret、password、auth、sig 等），再寫入任何欄位。
4. **單筆長度：** 結構化事件的說明最多 300 字、自由文字最多 200 字，以字元（code point）計。超過就截斷並加上 `…`。這取代目前暫定的 1000 字。
5. **匯出：** 匯出到 Mantis 或 Notion 時，預設**不含** `## 流程紀錄` 與 `## 異動專案`（內含絕對路徑與機器名）。
6. **整併遮蔽邏輯：** 把 `publicText` 與 `redactHandoffSecrets` 合成單一模組，補上漏掉的樣式，加專門測試；session handoff 也使用同一個模組。這是獨立於卡片的 PR。
7. **限制：** 任何偵測都不完整。規則 1 是主要防線，規則 2 到 3 是補強；偵測失敗時卡片仍可能含機敏文字，所以卡片目錄維持 0700／0600、不進 git、匯出預設排除 bridge 區塊。

## 後果

- 好處：不需要為狀態變動開 PR；不弄髒工作樹、不影響版本指紋；內容不進公開 repo；沒有 git 歷史衝突；多機器不需同步；格式與已寫好的程式幾乎都能沿用。
- 代價：卡片沒有 git 歷史，流程紀錄必須自己累積；卡片的備份依賴狀態目錄本身；卡片與 journal 是兩份記錄，需靠「journal 為權威、卡片衍生且冪等」避免不一致；流程紀錄會成長，因此需要提高上限並在超過時輪替到旁檔（決定 10），輪替增加了實作複雜度。

## 替代方案

- **專案 repo 內 `.gitignore` 的資料夾**：每個專案各一份；一張卡改多個專案時沒有自然的位置；多機器各一份。
- **獨立的私有 cards repo**：每次狀態變動要 commit（若有 ruleset 還要 PR）與同步，成本高。
- **SQLite 等資料庫**：不符合 ADR-0001 對可攜、可匯出匯入 md 的要求。使用者以 log DB 作比喻，指的是「帳本」的角色，不是儲存技術。

## 驗收條件（實作時）

- 卡片建立於 `<stateDirectory>/cards/`；目錄 0700、檔案 0600；不寫入此目錄以外的位置。
- 開單到結束的各階段都在 `## 流程紀錄` 留下紀錄；同一事件重複寫入不產生重複行。
- 人在編輯人寫區的同時 bridge 追加紀錄：雜湊衝突被偵測，不丟失人的修改（沿用 `CardStore.update`）。
- `projects` 欄位與 `## 異動專案` 對應實際被改的專案與機器；`project`（舊欄位）仍可讀。
- 卡片不在任何專案 repo 內，專案的 `git status` 不因卡片而變髒。
- 執行中的卡片被刪除時暫停並詢問，不默默繼續或取消。
- 流程紀錄達到輪替門檻時，舊紀錄移到 `logs/<id>/` 旁檔，卡片保持可解析且不超過硬上限；旁檔不被 `list()` 當成卡片。
- 輪替後卡片恰好保留最近 5 筆紀錄（不足 5 筆時全部保留），較舊的全部在旁檔，旁檔依序編號、內容不重不漏。
- 輪替兩步之間模擬崩潰：同一批紀錄同時存在於旁檔與卡片，讀取以事件 id 去重後沒有重複。
- 旁檔寫入失敗時拒絕追加並回報，卡片不被寫壞。
- 匯入使用 512 KiB 上限，營運卡片使用 1 MiB，兩者不互相放寬（已有自動化測試：營運用 store 的 `importText` 仍受匯入上限限制）。
- 寫入的紀錄不含機敏內容（規則見決定 11）：
  - 結構化事件之外的文字命中機敏樣式時，整筆說明改為固定訊息，事件時間、事件名與事件 id 仍保留。
  - 網址的帳密與像 token 的查詢參數在寫入前被移除。
  - 共用的遮蔽模組對上述 15 類樣本（含 `github_pat_`、AWS key、JWT、單獨 `Bearer`、`API_KEY=`、`secret_key:`、網址帳密、連線字串、私鑰區塊）都有測試，並確認 commit SHA 與一般句子不被誤改。
  - 結構化事件說明不超過 300 字、自由文字不超過 200 字，超過截斷。
  - 匯出到 Mantis 或 Notion 預設排除 `## 流程紀錄` 與 `## 異動專案`。

## 與 ADR-0001 的關係

| 7. 刪除語意 | 補充：位置改為狀態目錄；執行中被刪的處理不變 |
| 8. 匯入匯出 | 不變 |

## 實作狀態（2026-11-02）

**已實作：檔案大小上限依用途帶入。** 其餘決定（營運卡片目錄、流程紀錄與輪替、`projects`、bridge 寫入）**都還沒實作**。

- `src/card.ts` 匯出 `IMPORT_MAX_FILE_BYTES`（512 KiB，預設）與 `LEDGER_MAX_FILE_BYTES`（1 MiB，也是絕對上限）、`ReadOptions`、`formatByteLimit`、`resolveMaxFileBytes`。`parseCard`、`readCardDocument` 接受 `{ maxFileBytes }`。
- 不合法的上限（非整數、小於 1、大於 1 MiB、`Infinity`、`NaN`）是程式錯誤，丟 `RangeError`，不會悄悄關掉保護。frontmatter 的 8 KiB 上限不受影響。

### 受限寫入與權限（2026-11-02）

- **權限：** `CardStore` 寫出的卡片檔為 0600，它建立的目錄為 0700（`update` 會把原本較寬鬆的檔案收緊為 0600）。測試在非 Windows 平台執行。
- **`setStatus(id, status, today)`**（bridge 專用）：只改 `status` 與 `updated`。只允許設成 `in_progress` 或 `done`，且只能 `ready → in_progress → done`；同一狀態重複設定是冪等的、不重寫檔案；`updated` 只會往後推。**這些轉換規則是 Agent 的預設，使用者尚未逐項確認。**
- **`appendLog(id, entries)`**（bridge 專用）：把紀錄追加到內文的 `## 流程紀錄` 區塊（沒有就在內文最後建立），事件 id 去重（冪等），沒有新紀錄時不重寫檔案；有新增時 `updated` 推進到最後一筆的日期。呼叫端**不需要先持有雜湊**：內部會重讀、遇到雜湊衝突（人剛好在編輯）自動重試，最多 3 次，仍衝突才回 `conflict`。
- **純函式 `appendLogEntries(body, entries)`**（`src/card-ledger.ts`）：區塊以外的內文逐字不變；全部欄位先驗證，有一筆不合格就整批拒絕；事件 id 只與該區塊內的既有紀錄比對，內文別處出現的 `ev:` 字串不會擋住追加；`## 流程紀錄備註` 這類只是前綴相同的標題不算同一區塊。
- **紀錄行格式（已實作）：** `- <UTC 時間> | <事件名> | <單行說明> | ev:<事件 id>`。時間須為真實存在的 `YYYY-MM-DDTHH:MM:SSZ`；事件名為小寫英數與底線（最多 32 字）；事件 id 為英數與 `-`、`_`（最多 64 字）；說明不得含換行、控制字元或 ` | `，長度 1 到 300 字（2026-11-02 由暫定的 1000 字改為決定 11 定案的 300 字）。
- **限制（已用特徵測試釘住）：** 寫入會重新序列化 frontmatter，因此**內文與所有欄位的值逐字保留，但 frontmatter 的註解與欄位順序會被正規化**（例如人加在 `status:` 後面的 `# 註解` 會在 bridge 下一次寫入時消失）。人要留註解請寫在內文。
- **通道不是強制的：** `setStatus`／`appendLog` 是 bridge 應該使用的受限通道，但泛用的 `update` 仍是公開方法，沒有被移除；「bridge 只動自己的區域」目前靠使用約定，不是型別或權限強制。

### 事件模板與內容規則（2026-11-02，決定 11 的卡片端，尚無呼叫端）

- **`buildLogEntry(event)`**（`src/card-events.ts`）：把有型別的事件轉成一行紀錄，說明由固定模板組出。14 種事件：`assigned`、`worktree_created`、`started`、`review_verdict`、`verify_result`、`pr_opened`、`ci_result`、`merged`、`blocked`、`resumed`、`failed`、`cancelled`、`cleanup_done`、`cleanup_pending`。清單是追蹤清單 C1 的提議，使用者 2026-11-02 回覆「照提議的做」，未逐項增刪。
- **`CardStore.recordEvent(id, event)`**：以上述模板記入 `## 流程紀錄`，沿用 `appendLog` 的冪等、重試與 `updated` 推進。低階的 `appendLog` 仍接受任意已驗證的說明文字，**不套用模板與機敏檢查**；bridge 應使用 `recordEvent`。
- **每個欄位都有嚴格格式**，不合格回 `invalid` 並指出欄位：機器 id、Agent 名稱、分支（最多 80 字）、commit SHA（7 到 40 位小寫十六進位，顯示前 12 位）、絕對路徑（最多 120 字，不含控制字元與 ` | `）、網址（http(s)、最多 150 字、無空白）、整數範圍、各列舉值。
- **單筆說明最多 300 字**。各欄位上限使最長的事件仍在 300 字內（測試涵蓋每個事件的最大值）。
- **網址先移除帳密與像憑證的查詢參數，再寫入**（規則 3）；網址放在說明最後，避免後面緊貼的文字被查詢參數規則吃掉。
- **唯一的自由文字是 `failed` 的短原因**：空白正規化、最多 200 字（超過取前 199 字加 `…`）。**機敏檢查在截斷之前**：測試證明若先截斷，被切斷的 token 會比對不到。
- **疑似機敏 → 整筆說明改為 `內容已省略：疑似含機敏資料`**：只要最終說明經 `redactSecrets` 會被改動，就整筆省略；事件時間、事件名、事件 id 仍保留，事件照常記錄。這個檢查套用在**所有欄位**，不只自由文字（例如分支名被命名成 token 的樣子也會觸發）。

### 輪替（2026-11-02，C6，尚無呼叫端）

- **觸發：** `appendLog`（含 `recordEvent`）追加後，若整張卡的序列化大小超過這個 store 上限的 75%（營運卡片 1 MiB → 768 KiB），就輪替。
- **做法：** 卡片的 `## 流程紀錄` 只保留最新 **5 筆**，其餘依序移到 `logs/<id>/NNNN.md`（編號四位、遞增），並在區塊開頭放一行 `> 較早紀錄已移到 logs/<id>/0001.md（只增不改）`（多個旁檔時寫 `0001.md 到 0003.md`），再次輪替時**取代**而不是疊加。旁檔開頭有標題行，其後是原樣的紀錄行；人寫的行、說明與區塊以外的內文保留。
- **順序：** 先確認結果放得進上限（放不進就整個拒絕，任何東西都不寫），再建旁檔（先寫暫存檔再 `link`，不覆蓋），最後用雜湊比對更新卡片；衝突時重讀重試，最多 3 次。
- **安全：** `logs` 或 `logs/<id>` 是符號連結回 `unsafe`、不是目錄或寫入失敗回 `io`，都不寫卡片；`logs/` 目錄 0700、旁檔 0600；`list()` 與 `existingIds()` 看不到旁檔（不在卡片目錄同層）。
- **`readLog(id)`**：回傳旁檔（依編號）加上卡片裡的全部紀錄，事件 id 重複的只留第一筆。
- **無法輪替的情況：** 區塊裡不到 5 筆可移，或人寫的內容太大，輪替後仍放不進上限時，回 `too_large`，卡片與旁檔都不動。
- **真實尺寸驗證（2026-11-02，一次性腳本，非自動化測試）：** 用營運設定（1 MiB 上限）、每筆 300 字、每批 200 筆連續追加 8000 筆。第一次輪替發生在累積 2400 筆時，卡片由 767,948 位元組降到 1,970；卡片最大 769,782，最大旁檔 837,654（小於 1 MiB）；產生 3 個旁檔；`readLog` 讀回 8000 筆且全部唯一。

- **限制：** 單次追加最多 200 筆；旁檔最多 9999 個；輪替後的重送冪等需要讀旁檔，旁檔很多時追加會變慢（只在卡片有指向旁檔的說明時發生）；旁檔目前沒有清理機制。
